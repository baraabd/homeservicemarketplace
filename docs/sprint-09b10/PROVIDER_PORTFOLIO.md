# Sprint 9B.10 — provider portfolio

A provider's public gallery of finished work, built on the existing
`ProviderPortfolioItem` model and the existing public-media pipeline.

---

## 1. The separation that shapes everything

**Portfolio media is `PUBLIC`. Verification evidence is `RESTRICTED`.** They
share one `MediaAsset` table and nothing else.

|               | Portfolio                         | Verification evidence                |
| ------------- | --------------------------------- | ------------------------------------ |
| Visibility    | `PUBLIC`                          | `RESTRICTED`                         |
| Key namespace | `portfolio/<ownerRef>/…`          | `verification/<caseId>/…`            |
| Read path     | `/v1/media/files/<key>`, no token | audited short-lived read (9B.3)      |
| Capability    | `EDIT_OWN_PROFILE`                | `MANAGE_VERIFICATION`                |
| Audience      | every customer                    | the owner and an authorised reviewer |

The direction that must be impossible is a portfolio item pointing at an
evidence asset: a provider who managed that would **publish their own identity
documents to the marketplace**.

So the check is on the storage **key**, not only on the visibility column. A key
is fixed at upload time, written by the server, and changed by no route. A
visibility column is a field, and fields get updated by code nobody re-reads.

`assertPublishableKey` refuses:

- the `verification/` prefix **by name** — including when it names the caller,
  because a provider publishing their own documents is still a disclosure they
  almost certainly do not understand;
- any namespace but the caller's own;
- traversal, absolute paths, null bytes and `//` — the presign endpoint
  synthesises keys and never echoes a filename, so a key containing any of those
  did not come from it.

Deletion is scoped the same way: the media update names
`{ ownerUserId, visibility: 'PUBLIC' }`, so a portfolio delete cannot mark an
evidence row for cleanup even through a deliberately mis-linked item. A test
mis-links one and asserts the evidence row is untouched.

## 2. The owner segment is an HMAC, not a user id

A portfolio image URL is handed to **every customer who views the gallery**. A
raw user id in that URL publishes an internal identifier that correlates the
provider across every other surface that ever exposes one.

`portfolioOwnerRef(userId, secret)` is a 24-hex HMAC: deterministic, so the
ownership check recomputes it rather than storing it, and one-way, so a URL
cannot be walked back to an account.

Request media keeps its existing `requests/<userId>/…` layout — those URLs are
shown only to the seeker and the bidding providers, and changing the scheme
would orphan every URL already stored in `ServiceRequest.mediaUrls[]`.

**This was found by a test**, not by review: the response-boundary assertion
listed the raw user id among the strings that must not appear on the wire.

## 3. API

| Method | Route                               | Capability         |
| ------ | ----------------------------------- | ------------------ |
| GET    | `/v1/me/provider/portfolio`         | `EDIT_OWN_PROFILE` |
| POST   | `/v1/me/provider/portfolio`         | `EDIT_OWN_PROFILE` |
| PATCH  | `/v1/me/provider/portfolio/:itemId` | `EDIT_OWN_PROFILE` |
| POST   | `/v1/me/provider/portfolio/reorder` | `EDIT_OWN_PROFILE` |
| DELETE | `/v1/me/provider/portfolio/:itemId` | `EDIT_OWN_PROFILE` |

Upload reuses `POST /v1/media/presigned-url` with `purpose: 'portfolio'` — a
**whitelist of two server-owned constants**, never a caller-supplied prefix.

`EDIT_OWN_PROFILE` rather than a capability of its own: a portfolio is profile
content, and Sprint 9B.8's route matrix already states what that capability
means in every provider state. A new capability would need its own row saying
exactly the same thing.

### Ownership is a WHERE clause, never a check

Every read and write is scoped to the caller's `providerProfileId` **inside the
query**. Not "load it, then compare the owner" — that pattern has an
if-statement someone can forget, and its failure mode is editing a stranger's
gallery.

"Not found" and "not yours" return the **same 404**, asserted by comparing both
responses field by field, so the surface cannot be probed for which item ids
exist.

### Idempotency and concurrency

The **storage key** is the idempotency key. It is already `UNIQUE` on
`MediaAsset`, so the database enforces the guarantee rather than application
code remembering to, and a client retrying after a network timeout still holds
it — whereas a client-generated token is regenerated by any retry that re-runs
the whole flow.

The replay is checked **before** the limit. Otherwise a retry of the create that
filled the last slot is refused for having filled it.

Covered: duplicate create, two concurrent creates, double delete, two concurrent
deletes, two concurrent reorders (positions stay dense and unique), repeated
update.

### Deletion is soft, and the bytes are marked rather than erased

A moderation decision was recorded against this image. Destroying the bytes the
moment a provider taps delete leaves a moderation record describing a file
nobody can look at again. The retention sweep owns the bytes; this owns the
intent.

Deleting twice is a no-op, not a 404 — a double-tap on a phone must not produce
an error the provider cannot act on.

## 4. Limits

| Setting                             | Default | Bounds         |
| ----------------------------------- | ------- | -------------- |
| `provider_portfolio_max_items`      | 12      | 1–60           |
| `provider_portfolio_max_file_bytes` | 5 MB    | 64 KiB – 10 MB |

Both can only ever **refuse**, so both fall back to their schema default on a
bad read: a settings outage must not empty every provider's gallery. (Contrast
Sprint 9B.9's preview policy, which can only ever _disclose_ and therefore fails
closed.)

A **lowered** ceiling refuses additions and deletes nothing. An operator
tightening a limit must not silently unpublish work customers were already
shown.

Images only — deliberately, even though the shared content-type module allows
video: videos need transcoding and a poster frame nothing here produces, and
shipping the type without the pipeline puts an unplayable file in front of a
customer.

## 5. Reordering converges instead of failing

A complete list of ids, not a moved-item delta: a partial reorder has to be
reconciled against a server order the client may not have, and the
reconciliation is where the bugs live.

- ids that are gone are **ignored** — a stale tab reordering a gallery someone
  deleted from on another device should agree, not 409;
- omitted live ids keep their relative order and land after the named ones, so a
  partial list cannot silently drop work out of the gallery;
- duplicates are collapsed, because two positions for one id is not an order;
- positions are always dense and 0-based, so a client can render by index.

## 6. Frontend

**Reused:** `ds/Button`, `ds/IconButton`, `ui/{badge,input,label,textarea,
progress,skeleton,alert-dialog}`, `useLang`, the `*-copy.ts` + key-parity-test
pattern from the onboarding wizard, and the existing presign→PUT upload
pipeline.

**New:** `portfolio-copy.ts`, `PortfolioSection.tsx`, `provider-portfolio-api.ts`,
`useProviderPortfolio.ts`.

States covered: loading, load failure with retry, empty, populated, limit
reached, upload progress, validation refusal, moderation badge, reorder, edit
caption, delete confirmation.

### Direction is never hard-coded

Reordering is where an RTL bug is invisible in review and obvious to a user:
"move earlier" moves an item towards the **start of the reading order**, which
is the **right** in Arabic. The controls are labelled by **intent**, the glyph
is derived from `dir`, and a Playwright test asserts it points the opposite way
in each language — one direction alone would pass against a hard-coded arrow.

### Errors render from codes, never server sentences

A server message arrives in one language whatever the UI is set to, so an Arabic
reader would get English. An unrecognised code falls back to generic copy: a
provider must never be shown `NEW_SERVER_CODE_2027`, and they are not the person
who can fix it.

### Three defects the tests found

1. `ds/Button` takes `state`, not `disabled`/`loading`/`type` — passing the
   React-native names silently did nothing, and a "disabled" confirm button
   stayed clickable.
2. It does not forward `aria-label`, so icon-only controls built from it were
   announced as their glyph. `IconButton` exists for exactly that.
3. The hidden file input and its visible trigger shared one accessible name,
   which announces "Add photo, button" twice with no way to tell them apart.

## 8. Residual risks

1. **Moderation is a state, not yet a workflow.** Items start `PENDING` and the
   UI renders all three states, but nothing in this sprint moves an item to
   `APPROVED` or `REJECTED`. Until an admin queue exists, every published item
   shows as "being checked".
2. **`publicationRightAckText` is a constant.** It records _that_ the provider
   confirmed, and the timestamp, but not the wording they were shown. If the
   consent text changes, older acknowledgements cannot be matched to what was on
   screen at the time.
3. **No image content inspection.** The declared MIME type and size are checked,
   the extension comes from the whitelist, and the key is server-minted — but
   nothing verifies the bytes are the image they claim to be. Portfolio media
   does not go through the 9B.4 malware pipeline, which is evidence-only.
