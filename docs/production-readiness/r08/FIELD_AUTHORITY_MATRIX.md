# R08 — Provider V2 field authority matrix

One row per field of the Provider Onboarding V2 application. `PASS` is given
only where the named test executed and asserted the stage; nothing here is
inferred from reading code.

Evidence spec: `apps/web/e2e/r08-provider-v2-all-field-authority.real-api.spec.ts`
(referred to below as **R08 spec**), run against the real API, PostgreSQL, Redis
and a web bundle built with `VITE_PROVIDER_ONBOARDING_V2=true`. The spec asserts
that the browser override `hsm.ff.providerOnboardingV2` is absent in every
browser context it uses.

Shared facts, true for every row unless the row says otherwise:

- **API DTO:** `PatchOnboardingStepDto`
  (`apps/api/src/modules/provider/onboarding/dto/patch-onboarding-step.dto.ts`).
- **Service method:** `ProviderOnboardingWizardService.patchStep`, which accepts
  a field only on the step that owns it (`STEP_WRITABLE_FIELDS`).
- **Server acknowledgement:** the `200` body of
  `PATCH /v1/me/provider/onboarding/steps/{STEP}`, which is the whole draft view
  after the write. The R08 spec waits for the acknowledgement whose returned
  value equals the value on screen.
- **Reload source and fresh-login source:** `GET /v1/me/provider/onboarding/draft`
  (`toData`), read by the task screen on mount. There is no client-side copy:
  the R08 spec reads every field back in a browser context that shares nothing
  with the one that wrote it.
- **Version / concurrency rule:** every step write carries the draft `version`.
  A stale version is refused with `409 CONFLICT` and
  `error.details.{expectedVersion,receivedVersion}`; the web client drops the
  stale edit and tells the provider to reload. A successful write advances the
  version by one.

## Authority under failure

| Scenario                         | What was proved                                                                                                                                                        | Evidence (R08 spec test)                                                 | Result |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------ |
| Stale second tab                 | The stale write is `409`, is not stored, does not advance the version; the tab says so and never says "Saved"; after a reload it shows the current value and can write | "a stale second tab cannot overwrite a newer write…"                     | PASS   |
| Offline                          | Status is "offline", nothing reaches the server; on reconnect the edit is written exactly once                                                                         | "an offline edit is never called saved…"                                 | PASS   |
| Lost response                    | The server commits once; the browser reports an error, not "Saved"; a retry is refused with `409` rather than applied twice; a reload reconciles                       | "a write whose response is lost is not duplicated…"                      | PASS   |
| Session loss                     | The write is refused, nothing is stored, the provider is sent to sign in, and after signing in sees the server value                                                   | "an edit made after the session is lost is refused…"                     | PASS   |
| Account isolation                | A second provider sees none of the first provider's values in the UI or the API, cannot edit or delete the first's portfolio item, and cannot claim its stored file    | "one provider can neither see nor change the application of another"     | PASS   |
| Arabic, English and limit length | Mixed-script values at the limit round-trip byte for byte through reload and PostgreSQL in an RTL session; one character over is `400` and changes nothing             | "Arabic, mixed and limit-length input is stored as documented…"          | PASS   |
| Completion is not work access    | After submission the profile is `PENDING_REVIEW`, the application is locked, and the provider work routes still answer `403`                                           | "REVIEW_SUBMISSION: consent and submission, which grant no work access"  | PASS   |
| Flag source                      | V2 is served with the browser override absent, in the writing browser and in the fresh-login browser                                                                   | "the built artifact serves V2 from its build flag…" and every `openTask` | PASS   |

## Not covered by this sprint

- Removing the profile photo, and reordering, retitling or deleting a portfolio
  item, are not driven through the UI by the R08 spec. Existing suites cover
  parts of them; they are not claimed here.
- Radius and coordinate matching (R09) and working-hours policy (R10).
- The legacy wizard and the legacy `/v1/me/provider/profile` route.
