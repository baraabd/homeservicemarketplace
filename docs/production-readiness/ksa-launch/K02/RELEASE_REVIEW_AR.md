## الأحكام السعودية التي تؤثر في القرار

- يطلب نظام التجارة الإلكترونية الإفصاح عن الهوية ووسائل الاتصال والبيانات النظامية ذات الصلة، وبيان تفاصيل السعر والتعاقد والفاتورة والمهنة المرخصة عند الانطباق. تُراجع أحكام العدول والتأخر والاستثناءات بحسب العقد ونوع الخدمة قبل اعتماد الاسترداد أو الإلغاء، وكذلك اختلاف دور المنصة بين وساطة الحجز وبيع اشتراكها. [النظام، المواد ٦–٩ و١٣–١٤](https://misa.gov.sa/app/uploads/2025/07/E-Commerce-Law.pdf)
- تشمل التزامات منصة الوساطة نشر حقوق الطرفين وآلية الشكوى وتسوية النزاع. بالنسبة إلى التعديل الجوهري للخدمات، توجد مهلة إخطار للمسجلين لا تقل عن أسبوع قبل التطبيق. تتناول اللائحة أيضًا حفظ بيانات العقود وأثرها. يُربط هذا الالتزام بفئة سجلات العقود عند إعداد جدول الاحتفاظ. [اللائحة التنفيذية بنشر أم القرى](https://uqn.gov.sa/wp-content/uploads/2022/10/%D8%A7%D9%84%D8%B9%D8%AF%D8%AF-4816.pdf)
- المادتان ١٢ و١٣ من نظام حماية البيانات الشخصية تتناولان إتاحة السياسة عند الجمع ومحتواها. المادة ٢٨ تقصر تصوير أو نسخ وثائق الهوية الرسمية على تنفيذ حكم نظامي أو طلب جهة عامة مختصة. المادة ٢٩ ولائحة النقل تنظمان النقل خارج المملكة. الإقرار بالاطلاع على الإشعار لا يمثل موافقة عامة على جميع الأغراض. [النظام](https://dgp.sdaia.gov.sa/wps/portal/pdp/knowledgecenter/details/PDPL) · [لائحة النقل](https://dgp.sdaia.gov.sa/wps/portal/pdp/knowledgecenter/details/RegulationonPersonalDataTransferOutsidetheKingdom)
- الأصل التعامل مع طلب الحقوق خلال ٣٠ يومًا. يسمح التمديد بما يصل إلى ٣٠ يومًا إضافية في الحالات المحددة مع الإخطار المسبق وذكر السبب. وتتناول اللائحة ضوابط إتلاف وثائق الهوية وتعيين مسؤول حماية البيانات. [اللائحة التنفيذية، المواد ٣ و٣١ و٣٢](https://dgp.sdaia.gov.sa/wps/portal/pdp/knowledgecenter/details/PDPL2)

## ما أُعد في فرع المراجعة

1. يتحقق الخادم من اكتمال اعتماد **الوثيقتين معًا** ومن مرجع غير فارغ لكل منهما ومعرّف إصدار غير موسوم بالمسودة. يتقدم غلق الإنتاج على إعداد تجربة المسودات. يظل رفض الإصدارات المختلفة من العميل برمز 409، قبل البحث عن البريد. إذا غاب الدور المرجعي `customer`، يتوقف التسجيل دون إنشاء حساب أو تسجيل قبول أو إرسال OTP.
2. يظهر تنبيه المسودة بحسب حالة الوثيقة وإصدار النص المعروض. بقيت الصفحات المعلوماتية غير المعتمدة موسومة للمراجعة. يميز نص مربع التسجيل بين الموافقة على الشروط والإقرار بالاطلاع على الخصوصية. تمنع اختبارات النصوص اعتماد إحدى الوثيقتين إذا بقي فيها وسم القرار المعلق المعروف في AR أو EN.
3. يستعمل الأمر `catalog:init` تعريف الفئات نفسه الذي يستعمله `seed`. المعاينة هي الوضع الافتراضي. يدرج وضع التطبيق الفئات المسماة المفقودة في معاملة واحدة. يتخطى المفتاح الفريد الموجود عند إعادة التشغيل أو التنافس. يعرض حالات `MISSING/ACTIVE/HIDDEN/GROUP/CREATED`. لا يحرر فئة قائمة أو يفك أرشفتها أو يدرج مستخدمًا أو مهنيًا أو صلاحية أو سياسة مهنية أو سوقًا. تعرض الشاشة الرئيسية الآن حالة تحميل أو فراغ أو خطأ قابل لإعادة المحاولة.
4. تستمر آلية التسجيل القائمة في تسجيل صفين مع إنشاء الحساب في معاملة واحدة. حقول الإثبات هي المستخدم ونوع الوثيقة ومعرّفها واللغة والمصدر ووقت الخادم. القيد الفريد `(userId, documentKind, version)` يحمي من تكرار الإثبات. لا يُعاد بناء موافقات الحسابات القديمة. علاقة الحذف مع المستخدم `ON DELETE CASCADE`، ولذلك يجب مواءمة حذف الحساب والاحتفاظ النظامي بسجل الإثبات قبل الوعد بمدة حفظ محددة.

## تشخيص الصفر وخطة التهيئة

`GET /v1/services` يقرأ من `ServiceCategory` ويعيد الصفوف التي تحقق `isActive=true AND deletedAt IS NULL`. لا يشترط وجود مهنيين أو تفعيل سجل السوق. عملية `migrate deploy` تنفذ ترحيلات المخطط؛ وجود ستة تعريفات في كود `seed` أو نجاح وظيفة الترحيل لا يثبت تطبيقها على قاعدة بعينها. تجربة R18 السابقة استعملت قاعدة محلية مستقلة. التهيئة العامة تحدث كذلك الأدوار والصلاحيات وتعيد تنشيط فئات وتصلح بيانات مواقع تاريخية؛ يُراجع أثرها مستقلاً عن الكتالوج.

| المشاهدة                                                  | اختبار التمييز                                                                                    | الإجراء المقترح                                                                                          |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| استجابة صحيحة بقائمة فارغة مع جاهزية سليمة                | مراجعة هوية خدمة Railway وقاعدة/مخطط Prisma وسجل الترحيلات، ثم عدّ الصفوف الإجمالية والظاهرة      | صفر إجمالي على الهدف الصحيح يرجّح نقص التهيئة؛ إجمالي موجب وصفر ظاهر يوجّه إلى حالة النشر أو الأرشفة     |
| 5xx أو فشل الجاهزية                                       | فحص اسم التبعية المتعطلة، الاتصال، امتياز القراءة، المخطط وسجل الترحيلات                          | إصلاح السبب ثم إعادة الطلب قبل اقتراح أي إدخال                                                           |
| خطأ DNS/CORS/TLS أو HTML/404 من الواجهة                   | مقارنة طلب Network الفعلي و`VITE_API_URL` المضمّن وقت بناء Vercel مع طلب مباشر للخدمة نفسها       | مراجعة عنوان البيئة وإعادة بناء الواجهة عند الحاجة. يمكن أن يحتفظ React Query بنتيجة سابقة لمدة ٣٠ دقيقة |
| فئات نشطة موجودة في القاعدة المراجعة، والـAPI يعيد فراغًا | مقارنة البيئة والمخطط اللذين يستخدمهما مثيل الـAPI، النسخة المنشورة، والطلب المباشر من نفس النطاق | معالجة توجيه البيئة أو اختلاف النشر قبل إدراج أي فئات                                                    |

استعلام تشخيص مقترح بصلاحية قراءة فقط على الاتصال نفسه الذي تستخدمه الخدمة. لا يُخرج حسابات أو وثائق أو أسرارًا. يُراعى المخطط الفعلي عند فتح جلسة SQL.

```sql
BEGIN READ ONLY;
SELECT current_database(), current_schema();
SELECT count(*) AS total,
       count(*) FILTER (WHERE "isActive" AND "deletedAt" IS NULL) AS visible,
       count(*) FILTER (WHERE NOT "isActive" AND "deletedAt" IS NULL) AS inactive,
       count(*) FILTER (WHERE "deletedAt" IS NOT NULL) AS archived
FROM "ServiceCategory";
SELECT slug, "isActive", "deletedAt" IS NOT NULL AS archived, "isLeaf"
FROM "ServiceCategory" ORDER BY "sortOrder", slug;
SELECT EXISTS (SELECT 1 FROM "Role" WHERE name = 'customer') AS has_customer_role;
COMMIT;
```

تجري المعاينة بعد بناء حزمة قاعدة البيانات وتوليد Prisma، مع تمرير اتصال الهدف المعزول صراحةً في البيئة. الأمر لا يحمّل ملف بيئة افتراضيًا.

```sh
pnpm --filter @homeservicemarketplace/database catalog:init --dry-run
```

مثال تطبيق للاختبار على قاعدة مؤقتة فارغة، بعد معاينة الهدف. المعرفان في هذا المثال يختبران الاختيار الجزئي. تحديد الخدمات التجارية عند الإطلاق قرار للمالك.

```sh
ALLOW_CATALOG_INIT=true pnpm --filter @homeservicemarketplace/database catalog:init --apply plumbing cleaning
```

قبل تطبيق أي فئات على الإنتاج، تُعرض هوية البيئة ورقم النشر، وأسماء الفئات الناقصة والمخفية والقائمة مسبقًا، وأثر الإدراج، ثم يصدر إذن منفصل. في حال الحاجة إلى الرجوع تُعطّل الفئات الجديدة التي أنشأها التشغيل عبر مسار الإدارة المدقق بعد مراجعة ارتباطاتها. تُحفظ الحسابات وسجل القبول والحجوزات.

## نتيجة الاختبار المعزول

- نجحت اختبارات IAM والتهيئة العامة ذات الصلة، واختبارات الواجهة للنصوص ونسخ التسجيل وحالات كتالوج العميل.
- على PostgreSQL 16.15 بعد الترحيلات من هذا المستودع، أظهر التشغيل التجريبي ست فئات ناقصة. أضاف التطبيق ست فئات ظاهرة؛ بقيت أعداد المستخدمين والمهنيين وسياسات التحقق والأدوار والأسواق وسجلات الموافقة صفرًا في تجربة الكتالوج. أعاد التشغيل التالي ست حالات `ACTIVE`.
- شغّل اختبار تكامل الأمر الفعلي على مخطط منفصل. غطّى منع الكتابة العرضية، والاختيار الجزئي، والتنافس بين تشغيلين، والحفاظ على صف مؤرشف باسمه ووقت تعديله.
- على API محلي مع PostgreSQL وRedis، رُفض الإصدار القديم، وعادت 503 عند غياب الدور الأساسي مع صفر حسابات وصفر موافقات. بعد تهيئة دور اختبار واحد سُجل عميل محلي بإقرارين عربيين وتوقيت الخادم، وحافظت إعادة المحاولة على الصفين. كان هذا المسار بوضع الاختبار مع المسودات؛ اختُبر فتح زوج معتمد ببيانات اختبار منفصلة في خدمة القبول. اختبار SMTP الخارجي والاعتماد النظامي من مسؤوليات مرحلة الإطلاق.
