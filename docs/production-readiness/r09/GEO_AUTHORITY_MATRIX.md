# R09 — Geographic authority matrix

One row per geographic concept that exists in the source. `PASS` is given only
where a named test executed and asserted the row; nothing is inferred from
reading code. All test coordinates are synthetic.

Evidence abbreviations:

- **IT-A** — `apps/api/test/integration/r09-geo-authority.integration.spec.ts`
  (real HTTP, real PostgreSQL).
- **IT-M** — `apps/api/test/integration/r09-geo-matching.integration.spec.ts`
  (real services, repositories, outbox worker and PostgreSQL).
- **E2E** — `apps/web/e2e/r09-work-area-geo-authority.real-api.spec.ts` (real
  browser, real API, real PostgreSQL, build-time flag, no override).
- **UNIT** — the unit spec named in the row.

## The authoritative model

Derived from ADR 0003, `apps/api/src/shared/geo/service-area.ts` and the
onboarding write path, then confirmed by the tests below.

| #   | Question                                         | Answer                                                                                                                                                                                                     |
| --- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Is the city authoritative?                       | Only as a fallback. It decides matching when the provider has no point and radius, or the request has no point. It is free text, normalised to a key (`trim` + lower case).                                |
| 2   | Are coordinates authoritative?                   | Yes, whenever the provider has a point and a radius and the request has a point. The city is then not consulted.                                                                                           |
| 3   | Is a market authoritative?                       | For what may be stored: the country must be an enabled market, and since R09 a point must lie inside the market's envelope when the operator has described one. The market does not take part in matching. |
| 4   | Is the radius stored or derived?                 | Stored. Derived by the server from the transport answer until the provider sets one explicitly; an explicit value is never moved again.                                                                    |
| 5   | Does transport affect the radius?                | It selects the server's suggestion only. Bounds (min, max) are operator settings; an earned ceiling can raise the maximum.                                                                                 |
| 6   | Are coordinates optional?                        | Yes. Completion requires a city, a country and a radius; not a point.                                                                                                                                      |
| 7   | Is manual selection allowed without geolocation? | Yes. City text, a map tap, a pin drag and "Use map centre" need no permission.                                                                                                                             |
| 8   | Can a point lie outside the typed city?          | Yes, by design (ADR 0003: a job across a municipal boundary must match). The server holds no geometry for a free-text city. The point decides matching.                                                    |
| 9   | Can a point lie outside the supported market?    | Not when the market is described: refused with `POINT_OUTSIDE_MARKET`. A market with no envelope cannot judge a point; the server then accepts it and says nothing.                                        |
| 10  | How is eligibility calculated?                   | Great-circle distance on a 6371 km sphere, unrounded, `distance <= radius`; otherwise city-key equality. A bounding box in SQL preselects, the exact distance decides.                                     |
| 11  | Does the list equal the detail?                  | Yes, for the provider's own service area. The list alone accepts a `near` city override for browsing, which never widens what can be opened (deliberate, documented in source).                            |
| 12  | Does a bid use the same rule?                    | Yes, the same repository predicate as the detail.                                                                                                                                                          |
| 13  | What happens without coordinates?                | City fallback. With neither a point nor a city the feed is empty and detail and bid answer 404.                                                                                                            |
| 14  | What happens with poor location accuracy?        | Nothing: `coords.accuracy` is never read, sent or stored, and no threshold exists. Recorded as a fact, not changed.                                                                                        |
| 15  | What location data is stored, and who sees it?   | See "Privacy" below.                                                                                                                                                                                       |

## Privacy

Unchanged by R09 except for one addition, which describes a country and not a
person.

| Data                               | Provider (own) | Admin review | Other providers                       | Seekers | Public profile | Logs |
| ---------------------------------- | -------------- | ------------ | ------------------------------------- | ------- | -------------- | ---- |
| Provider starting point (lat, lng) | yes            | yes          | no                                    | no      | no             | no   |
| Provider radius                    | yes            | yes          | no                                    | no      | no             | no   |
| Provider city and country          | yes            | yes          | —                                     | yes     | yes            | —    |
| Market envelope (new)              | yes            | —            | yes (same for everyone)               | —       | —              | —    |
| Request point                      | —              | —            | to providers who can open the request | owner   | —              | no   |

The point-invalidated log line added by R09 carries the profile id and a reason,
and no coordinate. The E2E suite records no trace or video and uses synthetic
coordinates only.

## Not covered, and why

- **City against coordinates.** No server-side check exists or was added: a
  free-text city has no geometry, and ADR 0003 deliberately lets a provider
  serve across a municipal boundary. The point decides matching; the screen
  asks the provider to check that the city matches.
- **A market with no envelope.** The server cannot judge a point and accepts
  it. Describing a market is an operator action.
- **One-finger panning.** Dragging on the map pans the map rather than the
  page. The map is 280 px tall, so the page scrolls around it. Unchanged.
- **Device accuracy.** No policy exists; none was invented.
- **Timezones, working hours and DST.** R10.
