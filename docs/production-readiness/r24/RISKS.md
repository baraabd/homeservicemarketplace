## Operational failure modes to preserve

An `UNKNOWN` dispatch is an unresolved external outcome. It must retain its provider key, operation identity if known and refund reservation. Creating a replacement obligation/key, manually marking failure or refund success, or deleting the uncertain record can duplicate an external effect or release reserved value prematurely. Use the same stored identity and verified recovery protocol.

A normalized event can remain `RECEIVED` when activation is missing or the transaction fails. It must remain available for retry. An R19 confirmation without matching committed R24 participant evidence is a reconciliation conflict, not permission to acknowledge activation. Notification intent commits in the transaction, but external outbox delivery is not proven by the fixture's worker-disabled tests.

A stored terminal refund observation may exist while its financial refund is still pending local compensation. Retain it and finish the local transaction; do not re-contact a rail merely to obtain the same proof. Contradictory terminal evidence must remain a conflict for reconciliation. Database constraints preserve evidence but do not validate an external provider's signature; that remains the configured adapter's responsibility.

Ledger financial totals are separate per currency and bounded by the accepted MoneyWire representation. Out-of-range stored projections fail closed rather than coerce through a JavaScript number. Reconciliation exception records have no accepted currency relation, so this view rejects a currency filter. Usage reads count accepted R19 records and do not decide the future R31 entitlement policy.
