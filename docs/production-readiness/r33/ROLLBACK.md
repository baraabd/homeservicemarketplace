# R33 — Rollback and recovery

R33 is additive and read-only. It introduces no migration, money mutation, permission grant, pricing change or irreversible data conversion. A rollback removes the new entry points and projections while preserving accepted money authority and all immutable financial history.

## Before merge

Keep the single R33 PR Draft while required evidence/integration is missing. Correct the same assigned branch with ordinary forward commits, or close the PR without merging if the owner decides not to take it. Do not force-push, delete another lane's work, rebase a concurrent lane or change `develop`.

## If an approved later release needs rollback

The owner/release coordinator must authorize the release change. Prepare a reviewed revert of the R33 feature commit(s), preserving unrelated accepted work. Review the actual integrated tree because other lanes may have subsequently bound capabilities to these surfaces.

1. Remove the two R33 navigation links from the leased Admin route-content and Provider wallet files, and the dedicated financial route registrations. The old booking reports and disabled withdrawal behavior remain usable.
2. Remove the `FinancialReportingModule` mount/import from AppModule. Existing `MoneyModule`, its R24 ports, ledger reads and command authority remain in place.
3. Remove the additive feature module, UI and shared financial-operations contract export only after confirming no accepted later lane consumes that contract. If later consumers exist, retain compatibility or coordinate their rollback first.
4. Remove the dedicated R33 browser CI step/artifact and matching mock-suite exclusion only with the feature removal. Preserve every pre-existing job, test, runtime pin, limiter, timeout, secret scan and official CodeQL requirement.
5. Run affected format/lint/typecheck/unit/build checks, existing entrypoint regressions, real-service authorization/read tests and required CI at the actual rollback head. Review AR/EN navigation and ensure no dead route remains.

Do not reverse the valid G2 owner-merge fact or reclassify an actually published acceptance as unpublished when reverting the feature. Coordination status must record the feature rollback separately. Preserve R33 evidence for audit.

## Data and privacy recovery

No ledger rewrite, refund cancellation, subscription-state rewrite, database reset, migration rollback, Redis flush or volume deletion is part of this rollback. Stored financial records stay authoritative and immutable under their original modules. No successful external payment is inferred from a UI status; no compensating adjustment is generated by the dashboard.

For an authorization incident, use the existing approved grant/session procedures and preserve audit evidence. Remove access before any feature availability change. CSV already downloaded by an authorized actor cannot be recalled by deleting a route. Never publish receipt contents, private notes, credentials or browser sessions while diagnosing.

## Disposable validation environment

Stop only recorded R33 process IDs and services created by this session: task API/SPA, task Mailpit, task Redis and task PostgreSQL. Each has an R33-only path and port. The isolated-database helper deletes only databases it generated after closing their clients. Do not reset the user's working database, flush shared Redis, delete another lane's storage or terminate unrelated processes. Runtime files and raw logs contain no publishable acceptance substitute; retain only sanitized hashes/counts and synthetic screenshots in the sprint evidence/CI artifact.

## Handoff after rollback

Record the rollback PR/head/tree, affected routes, executed tests and remaining limitations. The coordinator reruns the combined candidate gate before re-enabling any downstream receipt, plan, refund or reconciliation link. Merge, deployment and live-money activation still require their separate explicit owner authorization.
